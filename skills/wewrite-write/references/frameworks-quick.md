# 八种框架速查

| 框架 | 适用 | 基本推进 |
|---|---|---|
| 痛点 | 读者有明确困难 | 场景 → 根因 → 解法 → 边界 |
| 故事 | 人物与变化是核心 | 冲突 → 选择 → 结果 → 含义 |
| 清单 | 读者要快速行动 | 目标 → 条目 → 用法 → 避坑 |
| 发布声明 | 福利、活动、限免、发布通知 | 事实 → 边界与例外 → 怎么用 → 截止时间 |
| 对比 | 需要做选择 | 标准 → A/B 证据 → 适用人群 → 建议 |
| 热点解读 | 事件正在变化 | 发生了什么 → 为什么 → 影响 → 观察点 |
| 观点 | 核心价值是判断 | 主张 → 证据 → 反方 → 边界 |
| 复盘 | 过程经验可迁移 | 目标 → 做法 → 偏差 → 学到什么 |

按读者问题选框架。框架是组织工具，不是必须填满的模板；材料不足时缩小主张，不用空话
补齐结构。

## 发布声明框架（福利 / 活动 / 限免盘点）

这类内容只回答三件事：**哪里免费、怎么免费、有啥免费**。读者要的是把条件说清楚，
不是被科普。

| 小节 | 写什么 | 不写什么 |
|---|---|---|
| 事实清单 | 哪些模型/额度免费、免费到哪天、什么时段、什么资格条件 | 模型的参数、跑分、能力评测 |
| 边界与例外 | 谁不适用（企业版、团队版）、哪个时段要等、免费额度有没有上限 | 选型建议（「A 类用户该选 X」） |
| 怎么用 | 入口在哪、要不要领、账号要求、哪个端 | 自部署、算力、框架适配、开源权重下载 |
| 截止时间 | 每条线各自到哪天，哪条先走 | 「顺便提一句」的补充 |

**几个常见错误：**

- **用「清单」框架顶替**——清单的价值来自条目数量，天生会想「再多讲一条」。发布声明
  的价值来自条件说清楚，条目不是越多越好。
- **为了凑字数扩议题**——没到上限不是缺点，说明该说的说完了。福利公告 900 汉字以内
  就够，短了不补，也不要拆开揉碎重复解释。
- **把"相关"当成"该写"**——自部署跟 DeepSeek 有关，但没人在福利公告里想读这个。
  判断标准：读者读完这一段，是否知道了新的、原本不知道的、**而且他本来就想知道的事**？
- **漏掉例外**——"免费"两个字最容易骗到企业订阅用户。资格限制必须写，且要显眼。

## 与 `content_type` 的关系

`brief.content_type` 决定长度上限和上面这张「不写什么」表，`framework` 决定小节怎么排。
`content_type: announcement` 时用发布声明框架，不要用清单。
